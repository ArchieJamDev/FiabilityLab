# FiabilityLab Developer Guide

**Version:** 1.0  
**Project:** FiabilityLab  
**Suite:** Lab  
**License:** GNU General Public License v3.0

FiabilityLab is a Jamovi module for the evaluation of measurement reliability and
inter-rater agreement. This guide defines the development contract for code,
interfaces, statistical workflows, reports and releases. It complements
[`CODE_STYLE.md`](CODE_STYLE.md) and [`CONTRIBUTING.md`](CONTRIBUTING.md).

## 1. Filosofía / Philosophy

FiabilityLab is educational scientific software, not a coefficient calculator.
Every analysis must help the user understand what was estimated, under which
assumptions, with what uncertainty, and what cannot be concluded from it.

FiabilityLab follows the Lab principles:

- scientific rigor and methodological evidence;
- transparency about data handling, assumptions and limitations;
- reproducibility of calculations, versions and reports;
- educational explanations for students and researchers;
- consistent Jamovi interaction and bilingual documentation;
- maintainable code and explicit testing;
- scientific integrity above convenience or attractive results.

FiabilityLab must not present any estimator as universally “good” or “bad”. The
choice and implementation of estimators remain subject to the project’s ongoing
methodological review. A coefficient is evidence about a defined source of
measurement error, not a substitute for validity evidence or substantive
judgement.

FiabilityLab es software científico y educativo, no una calculadora de
coeficientes. Cada análisis debe explicar qué se ha estimado, bajo qué supuestos,
con qué incertidumbre y qué conclusiones no son admisibles.

## 2. Arquitectura del proyecto / Project architecture

The current repository follows the Jamovi module layout:

```text
FiabilityLab/
├── R/                         # generated headers and analysis engines
├── jamovi/                    # .u.yaml, .a.yaml and .r.yaml definitions
├── inst/                      # package resources and translations
├── build/                     # generated, disposable build artifacts
├── DESCRIPTION               # R/Jamovi package metadata
├── NAMESPACE                 # package exports and imports
├── *.jmo                     # distributable Jamovi module
├── Compilar_FiabilityLab.sh  # local build entry point
├── DEVELOPER_GUIDE.md
├── CONTRIBUTING.md
└── CODE_STYLE.md
```

`R/*.h.R` files are generated by Jamovi tooling and must not be hand-edited
unless the generator workflow explicitly requires it. `R/*.b.R` files contain
analysis logic and are the primary implementation surface. The `build/`
directory and `.jmo` files are outputs, never the source of truth.

The three YAML layers must remain synchronized:

- `.a.yaml` declares option names, types, defaults and admissible values;
- `.u.yaml` arranges those options in the user interface;
- `.r.yaml` declares result objects, tables, images and visibility rules.

`0000.yaml` connects analyses to the module menu. A change is incomplete until
the corresponding R implementation, generated header, UI, results and manifest
are consistent.

## 3. Estructura de un análisis Jamovi / Anatomy of an analysis

Each analysis normally has four coordinated parts:

```text
analysis.a.yaml  -> option contract
analysis.u.yaml  -> visual interface
analysis.r.yaml  -> result contract
analysis.b.R     -> validation, computation and reporting
```

An analysis should expose a stable pipeline:

1. validate variable count, type, level and option combinations;
2. prepare data without silently changing its meaning;
3. describe missingness and exclusions;
4. compute diagnostics and estimators only when their conditions are met;
5. quantify uncertainty where a supported method is available;
6. populate results in the order declared by `.r.yaml`;
7. generate interpretations, limitations and references;
8. render optional graphics as diagnostic tools, not decoration.

The R engine must use the public API supported by the declared Jamovi/jmvcore
versions. Result objects must be tested against the actual runtime, not only
against successful package compilation.

## 4. Flujo de desarrollo / Development workflow

Use this sequence for every change:

```text
Question -> evidence review -> estimand and assumptions -> interface design
-> implementation -> numerical validation -> report and translations
-> integration tests -> review -> release decision
```

Do not begin with code. First record the scientific question, unit of analysis,
measurement level, missing-data policy, estimand, uncertainty method and known
limitations. If the evidence review does not support a clear decision, document
the uncertainty instead of inventing a default.

## 5. Flujo estadístico de FiabilityLab / Statistical workflow

The common FiabilityLab workflow is:

1. identify the observational unit and the measurement design;
2. validate item/rater variables and their coding;
3. report sample size, number of items/raters and missingness;
4. inspect response distributions, sparsity and admissible categories;
5. assess dimensionality or agreement-design requirements where relevant;
6. compute only estimators selected by the user and supported by the data;
7. report uncertainty, warnings and sensitivity information;
8. interpret magnitude in context, never by a threshold alone;
9. provide methodological recommendations and limitations;
10. attach the relevant evidence and software references.

This workflow is deliberately estimator-neutral. The definitive set of supported
coefficients must be approved in a separate methodological review.

## 6. Internal Consistency

Internal Consistency concerns the coherence of items intended to measure a
common construct. It is not proof of unidimensionality, validity, temporal
stability or agreement between raters.

The design must distinguish:

- continuous or approximately continuous item responses;
- ordinal/Likert responses and sparse category patterns;
- genuinely dichotomous items and merely binary-coded data;
- item-level diagnostics and scale-level reliability;
- total-scale and subscale interpretations;
- complete-case, pairwise or model-based handling of missing data.

Before any estimator is enabled, the analysis should state its data conditions.
Dimensionality diagnostics may inform interpretation, but must not silently
replace the user’s selected model. Item-total correlations, item distributions,
response frequencies and “if deleted” quantities must be labelled as diagnostics,
not automatic item-removal recommendations.

Any future implementation of ordinal or dichotomous reliability must be
validated against independently calculated reference results and documented with
the exact correlation, covariance and missing-data choices used. Existing
implementations are provisional until that review is complete.

## 7. Inter-Rater Agreement

Inter-Rater Agreement evaluates the consistency or agreement of ratings produced
by multiple raters for the same observational units. The design must explicitly
separate:

- nominal, ordinal and continuous ratings;
- agreement versus consistency;
- two-rater versus multi-rater designs;
- fixed versus random rater interpretations;
- complete rating matrices versus missing ratings;
- pairwise, averaged and overall summaries.

The interface should require enough information to identify the design and should
explain when a requested coefficient is not appropriate. No coefficient list is
declared here: each future estimator must pass methodological review, numerical
validation and interface review before publication.

Reports must discuss prevalence, marginal distributions, weighting decisions,
missing ratings and the distinction between statistical significance and practical
agreement.

## 8. Estándares de interfaz / Interface standards

Use the common Lab order:

```text
Variables -> design and measurement level -> estimators -> diagnostics
-> uncertainty -> plots -> interpretation -> references
```

Controls must have explicit defaults, bilingual labels and predictable enabling
rules. Avoid presenting an option that is not implemented. Warnings should be
specific, actionable and visible near the affected result. Tables must have stable
column names, documented formats and no unexplained empty rows.

## 9. Generación de informes / Report generation

Every report should answer:

1. What data and design were analysed?
2. What was computed and why?
3. How uncertain or conditional is the result?
4. What does it support, and what does it not support?
5. What should the researcher examine next?

Reports must contain data-quality notes, estimator conditions, interpretation,
limitations and references. English and Spanish text must communicate the same
scientific meaning. A translation must never soften a warning or add a claim.

## 10. Interpretaciones metodológicas / Methodological interpretation

Interpretations must not reduce reliability to a universal cutoff. Discuss the
construct, intended use, number and quality of items/raters, sample size,
dimensionality, missingness and uncertainty. Distinguish reliability from
validity, responsiveness and substantive importance. Explain when a high value
may reflect item redundancy or restricted variability.

Recommendations must be phrased as conditional methodological guidance. They must
not instruct automatic deletion of items, raters or observations without evidence.

## 11. Documentation and evidence

Documentation is part of the implementation. New analyses and estimators require:

- a user-facing explanation;
- a developer explanation of the estimand and algorithm;
- primary methodological references and software references;
- assumptions, limitations and missing-data rules;
- examples or test fixtures;
- bilingual text reviewed for semantic equivalence.

Do not claim support for a method merely because a package function exists. Record
package versions, transformations and any deviations from published definitions.

## 12. Coding standards, testing and version control

Follow [`CODE_STYLE.md`](CODE_STYLE.md). Tests must cover parsing, option/YAML
consistency, normal and boundary inputs, missingness, unsupported designs,
numerical reference cases, bilingual output and Jamovi result-object integration.

Every change should be small and traceable. Commit or review descriptions must
state the scientific motivation, files affected, evidence used, validation
performed and remaining risks. Generated artifacts should be rebuilt only from a
clean, documented environment.

## 13. Scientific integrity

Never tune an algorithm to reproduce a preferred coefficient. Never hide failed
estimators, dropped cases, invalid categories or warnings. Never report a method
as supported until its definition, implementation, evidence and tests agree.
When the literature is divided, expose the disagreement and let the user make an
informed choice.

## 14. Release checklist

- [ ] Methodological review approved the estimand and assumptions.
- [ ] No unsupported estimator is exposed in the UI.
- [ ] `.a.yaml`, `.u.yaml`, `.r.yaml` and R code are synchronized.
- [ ] Generated headers and JavaScript are rebuilt from source.
- [ ] R syntax, YAML and JavaScript checks pass.
- [ ] Runtime tests pass with the target Jamovi/jmvcore versions.
- [ ] Numerical results agree with independent reference calculations.
- [ ] Missing-data and boundary cases are tested.
- [ ] English and Spanish reports are equivalent and reviewed.
- [ ] Documentation, references and version metadata are updated.
- [ ] The `.jmo` is inspected for required dependencies.
- [ ] Release notes state known limitations and unresolved risks.

## 15. Future development

Future work may expand diagnostics, estimator coverage, simulation-based teaching,
design-specific agreement reports and richer evidence navigation. Such work must
remain subordinate to validated definitions, transparent assumptions,
reproducible computation and Jamovi compatibility. No future feature is accepted
solely because it is popular, easy to calculate or available in an external
package.

---

FiabilityLab grows by making reliability reasoning more transparent, not by
maximising the number of statistics displayed.
